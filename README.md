# repo-standards

An org-neutral engine for repo-scoped agent standards. Each organization keeps a small overlay (`org.json`, data only) in its own standards repository and pins an engine release; the engine renders and applies the pack from it. The optional `launcher` key holds that org's own launcher settings (each org runs its own launcher deployment); the engine validates it on every load and never writes it into repositories:

```json
"launcher": {
  "repos": "*",
  "dispatch": [{ "repo": "standards", "workflow": "sync.yml", "every": "1d", "ref": "<branch>", "when": "drift" }],
  "sections": ["Goal", "Acceptance criteria"], "uiPaths": ["<glob>"],
  "duplicates": { "apps": ["<app slug>"] },
  "revert": { "newIssueEvents": 5, "eventFactor": 5 },
  "retro": { "approvers": ["<login>"], "engineApprovers": ["<login>"], "provider": "claudeAgent", "model": "<model id>", "effort": "<effort>", "repo": "<repo>" }
}
```

Every key is optional. Lanes, models, effort, the reviewer and the unassigned lanes are not standards: each org's launcher owns them and they are set on its dashboard, so an overlay with `launcher.lanes`, `launcher.review` or `launcher.unassigned` is refused. **Upgrade order (a prerequisite):** an overlay that still has any of the three keys fails to load under this engine, which stops sync, expiry and org-apply. So: (1) the launcher reads its lanes, reviewer and unassigned from its own dashboard config, migrated and verified; (2) each org releases an `org.json` without the three keys while still pinned to the old engine; (3) only then bump the engine pin, prove sync on one repository, then roll out to the fleet. `revert` holds the launcher's thresholds for reverting a production deploy (positive numbers; the launcher owns the defaults). `retro` configures the launcher's weekly retro. `approvers` approve repo- and pack-level rule changes, and `engineApprovers` approve engine-level ones; both are non-empty lists of GitHub logins. `provider` is `claudeAgent` only (the launcher refuses codex as drafter), with a non-empty `model` and optional string `effort` and `repo`. A dispatch entry's `when: "drift"` fires it only when some repository's `standards.lock` is missing or behind the entry repository's latest release. Unknown keys, schedules other than `<n>m|h|d`, and credential-looking values are refused. Other top-level keys the engine does not read pass through untouched.

## Consumer repositories

Every managed file is committed, so offline cloud sessions and sandboxes have everything: the managed `AGENTS.md` block, `.agents/skills/std-*` (+ `.claude/skills` link), `scripts/agent/` (`setup.sh`, `check.mjs`, `staging.mjs`, `cleanup.mjs`, `fresh.mjs`, `pins.mjs`, `gate.mjs`, `review.mjs`, `release.mjs`, `portal-pass.mjs`, `pr.sh`, `evidence.mjs`, `pack.json`), `.github/workflows/std-gate.yml` (the one required check, `gate`), `std-preview-cleanup.yml` (repositories with a Worker), PR/issue templates, `.claude/settings.json`, `.codex/config.toml`, `.codex/rules/std.rules`, the managed CODEOWNERS block (with `ui_owners`), and `standards.json` (repo-owned; states the pack version) + `standards.lock` (sha256 per managed path, engine version). Consumers never fetch the engine; only the org's sync job does:

```sh
npx -y github:tyler-b4innova/repo-standards#vX.Y.Z sync --overlay org.json --version <org release>   # GH_TOKEN = org App token
npx -y github:tyler-b4innova/repo-standards#vX.Y.Z apply --target <repo> --overlay org.json --version <org release>
```

**The standards repository gets its pack from sync like every other repository** (only `fleet.exclude` leaves a repository out): a pin pull request there changes only the overlay (`org.json`, the release version), and the sync App lands the repository's managed files in its own `standards/v*` pull request.

**Org contract:** run `sync` (and `expiry`) from a `workflow_dispatch` / `repository_dispatch` workflow in the org's standards repository, triggered by the org's dispatcher or a release. Never rely on `schedule`: it has not fired for either org. Credentials: repo variable `STANDARDS_APP_CLIENT_ID`, secret `STANDARDS_APP_PRIVATE_KEY`; `expiry` reads each credential's issue date from the env var named by `issued_var` (pass `vars.<name>` in the workflow). `org-apply` (from `org/`) reconciles the org's rulesets, `flow` property and App settings. Sync applies only a released overlay with the engine version it pins, and a pack landing runs no gate (the engine's own CI is the release gate): per repository it commits the pack on the default head, requires the repository's offline check (`setup.sh --check`) to pass on that commit, and fast-forwards the default branch, re-applying once if the branch moved. Repositories with no `standards.json` (outside the fleet) get a "not in fleet" row in the compliance issue and nothing else. A failing check opens one PR for a person; only the App may push `standards/v*`, so the person branches from it, commits the fix, opens their own PR and closes the sync's (its body gives the commands). An engine release marked `"breaking": true` in its `package.json` (it can stop a repository's gate or check from passing: a new required step, a trigger change, a new `--check` failure class) lands only with `--repo` until a person runs sync with `--proven` (recorded in the compliance issue, so later scheduled syncs follow; until then they sync nothing): prove it on the org's sandbox first, and open fix PRs for repositories the new rules would fail. The org App needs ruleset bypass on the default branch, `contents`/`workflows`/`actions` write, and the repos need `std-gate.yml` (managed).

**Precedence:** restrictions are additive (engine, then overlay, then repo can only add). Data is repo-owned and replaces: `standards.json` `ui_paths` (explicit `[]` = no UI, with a `--check` warning), `profile`, `dispatch`, `sensitive`, `e2e`, `flow`, `design_signoff`, `allow_paths` (globs exempt from the `.mcp.json` and forbidden-path checks, for shipped content such as a client plugin's `.mcp.json`), `deploy_workflow` (the one repo workflow allowed to build on push; it must not test), `risk_paths`, `production_urls` (absolute https URLs the org launcher smoke-tests after a production deploy), `nested_instructions` (`[{path, reason}]`: the only `AGENTS.md` or `CLAUDE.md` files allowed below the root; `--check` fails any other, and a `CONTEXT.md` at any depth), and `e2e` as an object: `{ "command", "browsers" (extra browsers, run on main against `staging_url`), "preview": false }` (a leftover `"budget"` is ignored with a warning), `affected` (`false`: pull requests run the full suite; or `{ "smoke", "foundations", "inert" }` glob lists; see Affected tests), `staging_url` (the https URL of the staging Worker, required with extra browsers), `overlay` (in a repository that carries the engine: the overlay file apply uses for it; the instructions step then lets an `AGENTS.md` change through only when it is exactly what apply generates at the pull request's head, so the engine's own copy follows template changes; the base commit supplies the renderer, the overlay, `standards.json` and the template, and the pull request only `template/AGENTS.block.md` as text, so a pull request that changes the renderer or the overlay never authorises an edit; the gate runs PR-supplied scripts, so this guard catches honest mistakes and is not a security boundary against a crafted pull request), `secrets` (`{"required": [names], "store": "1password" | "secrets_store"}`, see Releases), `staging` (`false`: a Worker not released through staging; its previews are still checked). `duplicate_check_exceptions` can preserve a named artifact-validation or release guard workflow as `[{"path":".github/workflows/validate.yml","sha256":"<64 lowercase hex>","reason":"why this must run separately"}]`; `--check` rejects a missing, malformed, or changed pin and still enforces timeouts, schedule frequency, browser installs, and managed gate integrity. Org overlay: `agents_md` (`"block-only"`: AGENTS.md is exactly the managed block, and `--check` fails on anything outside it), `ui_owners`, `risk_owners`, `gate.budget.e2e`, `gate.timeout_minutes` (the gate job's timeout, 5 to 120 minutes, default 30), `preview.check_name` / `preview.check_app` (the Cloudflare App slug whose Workers Builds checks count as deployment evidence, default `cloudflare-workers-and-pages`) / `preview.comment_author` / `preview.cleanup`, `e2e.release_browsers`, `portal`.

## Gate and review

`gate` (Actions) is the one required check: it checks the code. The org rulesets also require every review thread resolved, and a code owner's approval on `main` for UI paths. Nothing but code changes starts Actions.

**Run-name contract:** a `pull_request` gate run is named exactly `gate pr=<n> base=<ref> head=<40-hex sha>`; other events keep GitHub's default name.

**`gate`** runs on a pull request's commits (opened, synchronize, reopened, ready_for_review), the merge queue, and a `workflow_dispatch` the org launcher sends after a base change (gate then tests the fresh `refs/pull/<n>/merge`); never on comments, reviews, edits or pushes. The required check is the job `gate`, which aggregates the others: it passes only when the `checks` job and the one `test` job each succeeded, on a ready pull request; a draft head always fails it (the cheap plan, the live draft flag, or checks skipped for a draft push), so a pull request marked ready by an Actions token, which fires no `ready_for_review` run, has no passing `gate` to merge on; a failure or any skip fails it, and a run cancelled by a newer one in its group posts no `gate` at all. `checks` runs the offline check, the instruction-file guard and a checksum-pinned secret scan of the PR's own commits; then the single `test` job (one checkout and install, with the cache restores) runs typecheck, build, `scripts/agent/gate.local.sh` (it builds whatever it needs), the Workers Builds preview step and the e2e suite last (none fails unless `"e2e": false`, which skips both the e2e step and the preview step). A push to a draft PR skips `checks` and `test` (skipped jobs bill nothing; before, the push and the `ready_for_review` that followed seconds later started two runs and the first was cancelled but billed): a draft is not gated at all: every job is skipped (nothing billed or red) and the skipped gate job is named `draft (not gated)` (GitHub shows a skipped job's expression name unevaluated), so no check named `gate` exists on a draft head and a pull request flipped to ready without a full run has nothing to merge on. A draft iterates with `gate.mjs local`, and `pr.sh ready` triggers the one full gate. There is no opt-in: the engine repository behaves like every consumer. Every job's timeout is the overlay's `gate.timeout_minutes` (default 30); it only stops a runaway job and is not a quality signal: no step has a time budget, and a slow suite is fixed by making its tests better, never by a limit. An overlay that still sets `gate.budget` loads, prints one notice and is ignored. The `plan` step runs drafts cheap (check, secret scan, syntax; the tail is skipped) until ready_for_review. e2e runs Chromium only (extra browsers run on main, in the release check, through `standards.json` `e2e.browsers`), only the affected tests (see Affected tests), against the head's Workers Builds preview when the Cloudflare comment has one (`PLAYWRIGHT_BASE_URL`/`BASE_URL`). Where the repository has Workers Builds (the check is on its base branch tip), the preview must pass: gate waits for the head's build (up to 8 minutes), fails on a missing, unfinished or failed one, and runs e2e against its preview URL, read from the bot comment's table by its header row (the "Preview URL", or "Deployment URL", cell of the row whose commit is the head; never a link to the Cloudflare dashboard, and "No Preview URL" or a missing column is no URL); a passed build with no URL for the head in the Cloudflare comment fails too, never falling back to a local run. A pull request whose changes are all non-deployable (`defaults.json` `non_deploy_paths`: root Markdown, `docs/`, `AGENTS.md`/`CLAUDE.md`, `.github` templates and CODEOWNERS, `LICENSE`, agent config) skips the preview and e2e steps with a notice naming the files. A build Cloudflare skipped (build watch paths) runs e2e locally; `e2e.preview: false` opts out of the preview, and `"e2e": false` opts out of both it and the suite. The runner is the org variable `STD_GATE_RUNNER` (default `ubuntu-24.04`); `std-cache-warm.yml` refreshes the npm cache when the default branch's lockfile changes. `--check` fails repository workflows that test beside gate (on pull requests, or on pushes to the default branch), schedules more frequent than daily, jobs without `timeout-minutes`, `playwright install` without a browser, and expired or unlinked `@quarantine` tags.

**Affected tests:** the e2e step runs only the specs a pull request changes, in one case: every changed file is an added or modified spec file (`*.spec.*` / `*.test.*`) under an `e2e/` directory (`scripts/agent/select.mjs` decides; `node scripts/agent/select.mjs` prints the selection and why, and the e2e step prints and summarises the same). Any other change (source, helpers, fixtures, setup or `globalSetup`, configuration, data, docs, a deletion or a rename) runs the whole e2e suite, still Chromium only on pull requests; the base branch is irrelevant. Unit tests and the repo checks in `gate.local.sh` always run in full. Narrowing applies only when `GITHUB_EVENT_NAME` is exactly `pull_request` (missing or empty means the whole suite): the merge queue, `workflow_dispatch` re-gates, a push, an unknown base and `"affected": false` run the whole e2e suite, still the Chromium project only (what the gate installs). Only `GATE_SELECT=full` (the release check) runs every Playwright project with no file filter (no `--project`, no positional `tests/e2e`). **Custom commands:** with `e2e` set to a command, or a package script that is not exactly a bare `playwright test` (`playwright test --grep @smoke` and `&&` chains are not) (client sites: `pnpm test:e2e --project=mobile --project=desktop`; a repo-owned selector such as `node scripts/test-select.mjs e2e`), gate adds no project or file arguments to it: it runs unchanged with `GATE_AFFECTED` (`scoped` or `full`) and `GATE_AFFECTED_E2E` (space-separated specs; empty with `full`) in its environment, and `GATE_SELECT=full` whenever the whole suite runs, so a repo-owned selector can honour them. The full suite runs once, after merge, in the release check.

**Local iteration:** run `node scripts/agent/gate.mjs local` on macOS or Linux (x64 or arm64). It runs the CI commands in order: `setup.sh --check`, `instructions`, `secrets`, `syntax`, `install`, `run typecheck`, `run build`, `gate.local.sh` (if present), the local Worker (skipped as `SKIP (no Worker)` when the repository has no root Wrangler config and no `release_workers`, or with `"local": false`), then the same `e2e` suite. Unlike CI's cheap drafts, local always runs the full sequence. Each step prints its result; the final line names HEAD and every result, with a non-zero exit on failure. The instruction guard checks the branch against the local `origin/HEAD` merge base (or `main`/`master`, else HEAD), including uncommitted instruction edits. Fetch your base before iterating; local itself never queries GitHub for a preview or PR.

`standards.json` may declare `"local": {"command": "wrangler dev --local --port 8787", "url": "http://127.0.0.1:8787", "ready": "/health"}`. All three fields are required; URLs must be http(s) on loopback, and readiness must be a path on that origin. With the key absent, gate runs the installed repo Wrangler's `dev --local --ip 127.0.0.1 --port 8787` on its config and probes `/`. Readiness requires 2xx, rejects redirects, and times out after 60 seconds (`GATE_LOCAL_WAIT_S` overrides it). An already-running server fails instead of testing stale code. Gate sets `PLAYWRIGHT_BASE_URL` and `BASE_URL`, then stops the entire server process group on success, failure or interruption. `"local": false` skips server startup for repositories without a Worker; their same e2e suite still runs (`"e2e": false` remains the separate suite opt-out).

No secrets are needed: use local D1, Durable Objects with SQLite, Queues, R2 and KV and, when needed, dummy local values in the repo's already-ignored `.dev.vars`. Gate never reads an org vault, strips Cloudflare credentials and preview context from its children, and disables Wrangler telemetry and update checks. The default `--local` disables all remote bindings ([Wrangler documentation](https://developers.cloudflare.com/workers/wrangler/commands/workers/)). Repo-owned commands, build scripts and e2e seams must also stay local: no deploy, remote bindings or remote Cloudflare calls. No mocks of what the repo owns: exercise its real Worker HTTP entry point with local bindings. Only services owned by third parties may be stubbed, through the repo's existing seams. Local runs bypass preview-only noindex probes and doc-only suite skips. Iterate with this gate and require a passing run before marking a PR ready.

0.8.7 is **breaking**: production promotion is a Preview-trigger build of `release/<sha>` (above), so a Worker's Preview trigger must build every branch except `main` and run `release.mjs preview`, and the org needs the new ruleset (`org-apply`) with `org_admin.release_app.id` set to the portal App before a release branch can be created; a Worker with a Durable Object migration or `exports` gets no main-release production version (promote deploys it in full), and one with migrations needs `CLOUDFLARE_API_TOKEN` in its main build to read live state.

0.7.11 is **breaking**: the new `local` data validation can stop a consumer's `setup.sh --check` (and gate) passing if it already has malformed or non-loopback `local` data. Repositories with the key absent keep passing their existing CI checks; CI commands and triggers are unchanged.

**Instruction files:** gate's `instructions` step (drafts too) fails a pull request that changes `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md` or `CLAUDE.local.md` at any depth, `.claude/agents|commands|rules/`, or the managed CODEOWNERS block, unless the org App (the overlay's sync App login) opened it from `standards/v*` (sync) or `retro/*` (an approved retro). It is the launcher's instructions-guard rule inside the one required check, so it needs no extra App permission and covers pull requests opened under the owner's own login. A person's fix PR for a failed sync passes when its `AGENTS.md` and managed CODEOWNERS block equal those files at the tip of the sync App's `standards/v<standards.lock version>` branch (trusted data read from the checkout, not code: only the org App may push `standards/v*`); a missing branch, another version or any difference fails.

**UI and risk approval:** with the overlay's `ui_owners` set (e.g. `["@octocat"]`), apply writes a managed block at the end of `.github/CODEOWNERS` (or the root or `docs/` one, if that is where the repo keeps it) giving the repository's UI paths (`standards.json` `ui_paths`, else the engine defaults) to those owners; ignored paths get owner-less lines, which also clear the repo's own owners for those paths (the last match wins). The repo's own lines stay above it; `--check` fails a line after it. The org rulesets require code-owner review on the default branch and `main`, so a UI change needs a person's approval before it merges. With `risk_owners` set, the same block then gives the risky paths (`standards.json` `risk_paths`, else the defaults in `defaults.json`: workflows, auth, payments, secrets and env handling, migrations, `wrangler.*` and `infra/`, CODEOWNERS itself, and the agent instructions and their enforcement: `AGENTS.md`, `CLAUDE.md`, `.claude/`, `.codex/`, `scripts/agent/`, `.agents/skills/std-*`, `standards.json`) to those owners; they come last, so they win. The UI part is left out when `ui_paths` is `[]`, `design_signoff` is `false`, or there are no `ui_owners`; the risk part when `risk_paths` is `[]` or there are no `risk_owners`. GitHub treats the requirement as met when the PR's author is the only code owner. `--check` guards the block; a `ui_paths` edit reaches it on the next pack landing (a release), not before.

**The review rule** is `scripts/agent/review.mjs`, exported as `repo-standards/review` for a launcher or merge helper to ask before merging: `reviewStatus({ api, owner, repo, pr })` is read-only and returns `null` (draft, closed, not engine-managed) or `{ state, description, sha, base, base_sha, target_url, details }`. Its settings come from the current base branch:
- **Codex review:** a completed Codex review exists for any commit of the PR (its summary shows Completed, or the bot submitted a review) and no Codex thread is unresolved (resolved means answered). The head and push time are not checked: each PR gets one review and fixes are not re-reviewed. Pending for 20 minutes without a review, then failure ("request a review"). Repos with no Codex reviews and `codex_review: false` pass.
- **Evidence:** a PR changing UI paths needs a comment by a trusted author with images pinned to a commit in its history: before and after at 400 and 1280px for web changes, before-N/after-N page images for documents, and no UI change after them.

The managed AGENTS.md block carries a `## Review guidelines` line telling Codex review to skip pack-managed paths: findings on those belong in this repository.

## Client sites

Repositories on the `client` profile get checks for the rules their instruction files used to state.
- **Offline, in `--check`:**
  - the Turnstile script is the versioned `/turnstile/v0/api.js`;
  - a CSS rule animated on a `view()`/`scroll()` timeline never sets `overflow: hidden`, and `html` never sets `overflow-x`;
  - mail goes out through one seam, the only file that calls `.send(` on a `send_email` binding. The seam must test the request hostname against the production hosts with `.includes`, `.has` or `===`, so non-production hosts never mail the client;
  - a site whose Worker runs code (`main`) on `@sentry/cloudflare` has all four error layers: the wrapper (looked for in the tracked source when the build generates `main`), the middleware (`src/middleware.*` or `src/middleware/`), the browser init, and its same-origin tunnel route.
- **In `gate.mjs run build`:** the built HTML in `dist/` carries no HTML comments, no comments in inline scripts, and no source-platform names. Inline scripts are read by `scripts/agent/jsscan.mjs`, a small lexer. The names are `defaults.json` `source_platforms` plus the overlay's `profiles.client.source_platforms`.
- **In `gate.mjs e2e`, against the preview:** the preview's home page says `noindex`, in its robots meta or its `X-Robots-Tag` header.

## Releases

One branch, `main`. Workers Builds runs the pack's `scripts/agent/release.mjs`; each Worker has two triggers (Cloudflare allows no more per Worker):

| Trigger | Starts on | Deploy command |
| --- | --- | --- |
| Production | pushes to `main` | `node scripts/agent/release.mjs main` (client sites keep their noindex guard in front of it) |
| Preview | pushes to every other branch | `node scripts/agent/release.mjs preview` |

`main` deploys staging and uploads (never deploys) a production version tagged with the commit. A person approves that version in the portal; the portal's GitHub App then creates the branch `release/<40-hex commit sha>` at that commit (already on `main`) and deletes it after the build. The Preview trigger builds the branch like any other, and `release.mjs preview` recognizes the name (`WORKERS_CI_BRANCH` matching `^release/[0-9a-f]{40}$`) and **promotes that commit to production** instead of deploying a Preview. The org ruleset `org: release branches (portal App only)` lets nothing but the portal App (`org_admin.release_app.id`) create, move or delete `release/**`; with no portal App set, nobody can. The build uses only the Builds token Cloudflare provides (`CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, which wrangler and the live reads need) and has no GitHub token; none may be added.

**Promotion** (`release.mjs preview` on a release branch) changes nothing remote until all of this holds: the branch's sha equals `HEAD` and `WORKERS_CI_COMMIT_SHA`; main released the commit, which is proved by the version main uploaded for it (the `workers/tag` annotation, read from the Cloudflare API) for every Worker that deploys as a version, and, when every Worker deploys in full (no version exists for a Worker with Durable Object lifecycle changes), by the commit being an ancestor of `origin/main` in the build checkout's git history (after a fetch of `main`; a checkout that cannot show it refuses); every Worker's bundle passes `wrangler deploy --dry-run` with the production config; production's live state is readable. The portal runs the release-check before it creates the branch, so promote does not. Then it applies the Worker's pending production D1 migrations (`wrangler d1 migrations apply <binding> --remote`) and deploys each Worker, supporting Workers first in `release_workers` order and the primary last: a version deploy of the uploaded version (`wrangler versions deploy <id>@100%`), then `wrangler triggers deploy` (crons, queue consumers, routes, custom domains) and the Worker settings API for the settings that differ from live, or, where Durable Object lifecycle needs it, a full `wrangler deploy` of the approved commit. It reports what changed. A failure after the first remote change reports which Workers were promoted; approving the version again promotes the rest.

**What the Builds token can do.** Cloudflare's default Builds token has Account Settings (read), Workers Scripts (edit), Workers KV Storage (edit), Workers R2 Storage (edit), Workers Routes (edit, all zones), User Details (read) and Memberships (read) ([Builds configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/#api-token)). That covers version deploys, full deploys, `triggers deploy` for crons, routes and custom domains, and the Worker settings API. It does not include D1 (edit) or Queues (edit), which production D1 migrations and queue consumer registration need: a Worker with a D1 database or a queue consumer needs a Builds token that has those permissions, or the promotion fails at that step (before any code is deployed, for D1). No new token is introduced; extend the Builds token a Worker already uses.

**Settings a version upload never applies.** `wrangler versions upload` and `versions deploy` apply code and bindings only. Cloudflare's multipart upload metadata lists `migrations`, `logpush`, `tail_consumers` and `tags` as not available to version uploads ([Multipart upload metadata](https://developers.cloudflare.com/workers/configuration/multipart-upload-metadata/)), and routes, custom domains and cron triggers are applied by `wrangler triggers deploy` ([Deployment management](https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/)); Wrangler's `triggers deploy` also registers queue consumers. Promote applies crons, queue consumers, routes and custom domains with `triggers deploy`, and observability, logpush and tail consumers through the Worker settings API, each only where it differs from live (routes cannot be read without a zone, so a Worker that declares them re-applies them every promotion). The main release warns where live production differs from the config.

**Durable Object lifecycle** is decided against production's live state, never commit history. Cloudflare cannot upload a version that creates, deletes, renames or transfers a Durable Object class, from `migrations` or from `durable-object` entries in `exports` ([Deployment management](https://developers.cloudflare.com/workers/versions-and-deployments/deployment-management/#durable-object-migrations)). The live state is the script's `migration_tag` in the Workers scripts API ([list scripts](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/methods/list/)). Main uploads no version for a Worker whose last declared migration tag is not the live one, or which declares DO `exports`; promote deploys the approved commit in full. Unreadable live state fails the build.

In 0.7.2, staging builds run with `CLOUDFLARE_ENV=staging`, using `standards.json` `build` or `package.json` `scripts.build`. Before deploying, release follows `.wrangler/deploy/config.json` when present and requires exactly `<production name>-staging` with no routes or custom domains overlapping production. Wrangler output must confirm that name. A separate build with `CLOUDFLARE_ENV` unset precedes production upload. `setup.sh --check`, and gate after its build, probe redirected builds and fail with build configuration guidance if environment selection is unsupported. The probe rebuilds staging and production with captured output. TOML main releases require Python 3.11+ to parse the target safely.

`main` applies the commit's D1 migrations to staging's databases, deploys the staging Worker (`wrangler deploy --env staging`), then uploads the production version (`wrangler versions upload`, tagged with the full commit SHA and `SENTRY_RELEASE`; the portal ties a version to its `release-check` through that tag, so a Workers Builds deploy command written by hand must pass `--tag "$WORKERS_CI_COMMIT_SHA"`, and `--check` warns where a repo file documents `versions upload` without `--tag`), built but not live. Going live is the release branch for the commit a person approved after reviewing staging (above), and rollback is deploying an earlier version. A config without `env.staging` still deploys the legacy `staging` Preview, with a warning, so triggers and configs switch in either order. `preview` deploys the branch's Preview under `release.mjs slug <branch>` (the same name the 0.6 trigger used). `std-release-check.yml` ships to every repository with a Worker and a `staging_url`: it runs only before a production promotion, the same for every repository (never on a push, a check-run or a schedule): whatever promotes a version (the portal's Releases approval, or the agent deploy) dispatches it with `workflow_dispatch` and the version's commit as `sha`, and waits for the `release-check` check-run on that commit; it waits for every Workers Builds check on the commit (a repository whose staging is not deployed by Workers Builds fails it); the verdict is written only by trusted jobs (`pre` and `post` run the default branch's workflow, check the sha is on the default branch before anything of it is checked out, and alone hold write tokens), while the `suite` job that checks out the sha holds `contents: read` only; then runs the repo's full suite (e2e and `gate.local.sh`, no test selection) in Chromium plus every extra browser (`e2e.browsers`, the overlay's `e2e.release_browsers`) against `staging_url`, and posts the check-run `release-check` on that commit (the job's own check lands on the default branch's tip, so the verdict is posted through the Checks API). The dispatch contract: `sha` is a required exact 40-hex input (anything else fails fast), the job checks out exactly that sha and fails, posting no verdict, unless the default branch contains it, a `release-check` check-run is created `in_progress` on it at the start and completed once (success, failure, or `neutral` with the reason when superseded or there is nothing to certify), and the run is named `release-check <sha>`. Only the version staging currently serves can be certified: a run whose commit a later commit's staging build has superseded is cancelled, and a rollback to an earlier version needs no `release-check` (rollbacks are ungated by design). One run per commit, and its timeout is runaway protection only. It certifies a commit only through that commit's own successful staging build, and cancels itself (neither pass nor red) when a later commit's staging build supersedes it or there is nothing to certify (every Workers Builds check on the commit was skipped or neutral); a repository with no Worker or no `staging_url` has none, and `--check` says so. The release check sets `RELEASE_CHECK=1` for its e2e and repo-check steps and the pull-request gate never does, so tests tagged `@a11y` skip unless `RELEASE_CHECK=1`. **The launcher/portal production deploy waits for `release-check` success on the version's commit, and accepts it only if it is that workflow's own: the check-run's `external_id` is a workflow run id, and `GET actions/runs/<id>` has path `.github/workflows/std-release-check.yml`, `head_branch` the default branch, event `workflow_dispatch`, display_title `release-check <sha>` and conclusion `success` (`node scripts/agent/release.mjs verify-release-check <sha>` checks exactly this, for the agent deploy path and the portal); anything unresolved means not certified.**

**`release.mjs`.** `release_workers` deploy before the primary, in their listed order, for the staging deploy and the production upload (the primary binds Durable Objects and Workflows that live on them, so a new class must exist there first); a preview deploys the primary only. A Worker that keeps its config only in a subdirectory (a trigger rooted at `workers/<name>`, no root config) is not supported yet: declared primaries are tracked in the engine issue repo-standards#103. **Sentry:** when the Builds trigger has the `SENTRY_AUTH_TOKEN` build secret (set once, Cloudflare-side, never in GitHub) and the Worker config holds the DSN `scripts/agent/sentry-setup` commits (`wrangler.jsonc` or `wrangler.toml`), then after every Worker upload has succeeded the main release creates the Sentry release for the commit (org from `pack.json`, project from the DSN's project id) and uploads the source maps of Wrangler's final bundle: the primary's production `versions upload` writes it to a clean `--outdir` with `--upload-source-maps` ([Wrangler `versions upload` flags](https://developers.cloudflare.com/workers/wrangler/commands/workers/)), and `sentry-cli` (from `node_modules`) uploads that directory, never a framework build directory. A repository not set up for Sentry prints nothing about it; one that is, but lacks the token, logs one notice and skips. Every Sentry request and the `sentry-cli` run are bounded by a hang guard of 60 seconds by default, changed with `RELEASE_SENTRY_TIMEOUT_S`; an expiry or failure is a warning and the finished release exits 0. **A failure part-way** (for example the second supporting Worker's staging deploy or production upload) leaves the release mixed; the build log then lists which Workers were updated or uploaded (with version ids) and which were not, and a re-run of the build deploys and uploads them all again. Nothing is restored or rolled back automatically.

**Staging is a Wrangler environment** (`scripts/agent/staging.mjs`, in `--check`): `env.staging` is a separate `<name>-staging` Worker with its own D1/R2/KV, queues and consumers, Workflows, cron, staging service bindings (`<service>-staging`) and sandbox keys, its own routes (never a production one; routes are inherited unless set) and every binding and var re-declared (they are not inherited). PR Previews inherit nothing and their service bindings and Workflows reach the bound Worker's production deployment, so `previews` binds every data binding to the resource `env.staging` uses and never carries queue consumers, cron or routes. `--check` fails any `env.staging` or `previews` entry naming a production D1/KV/R2/queue, Workflow or Worker. `examples/wrangler.staging.jsonc` is the shape for a data app. A brochure site (no data bindings) needs nothing by hand: apply inserts its `env.staging` (workers.dev, `routes: []`, its vars and bindings) and `previews`, keeping comments; a data app's `--check` names the staging resources to create (`cf` CLI) and its sync opens a PR. `staging_url` becomes the staging Worker's URL.

In 0.7.3, staging secret checks address exactly `<name>-staging` with `--name` and no `--env`, including adapter-generated configs. A brand-new staging Worker with required secrets is created by the staging deploy with a private secrets file when Builds has `OP_VAULT` and `OP_SERVICE_ACCOUNT_TOKEN` configured. Otherwise release stops with bootstrap guidance before any production upload. For a one-time bootstrap in the CI build context, build staging first (`CLOUDFLARE_ENV=staging npm run build`, or the repository's configured build command), use the staging build already validated by the release guard, unset `WRANGLER_CI_OVERRIDE_NAME`, `WRANGLER_CI_MATCH_TAG` and `CLOUDFLARE_ENV`, create a private empty env file and a private JSON file containing the required secret values, and run `npx wrangler deploy --env staging --secrets-file <file> --dry-run --name <name>-staging --env-file <empty-env-file>`. Verify it targets exactly `<name>-staging` and isolated staging resources, then run `npx wrangler deploy --env staging --secrets-file <file> --name <name>-staging --env-file <empty-env-file>`. For a secondary Worker, append `--config <its-config>` to both commands. Remove the secrets file and re-run the build. Production upload never receives this secrets file.

For multiple Workers, list additional repo-relative configs in `standards.json` as `"release_workers": ["workers/runtime/wrangler.jsonc"]`. Main releases first build and snapshot production resources, then build staging, guard every target before any deployment, deploy each `<name>-staging` Worker, rebuild production, then upload each production version for review. Explicit secondary configs bypass the primary adapter redirect. Only the primary production `versions upload` receives `WRANGLER_CI_OVERRIDE_NAME` and `WRANGLER_CI_MATCH_TAG`; builds and every other Wrangler command receive neither. Each secondary config declares its own staging resources and required secrets. Cross-account staging isn't supported yet: release and `--check` reject staging or secondary `account_id` values that differ from the primary root `account_id`, including generated configs, before any remote command. Staging may inherit its root account; secondary configs must use the same root account selection.

Release commands use a private empty `--env-file` so Wrangler cannot reload name, tag or account overrides from `.env` files. The staging guard checks bindings and consumers in the resolved build output against source and generated production resources before any remote command. Durable Object transfer migrations cannot move objects from a production Worker into staging; malformed transfers are rejected.

The brochure migration copies `secrets.required` into `env.staging` and repairs declarations missing from 0.7.1 migrations without changing existing settings; `--check` rejects missing declarations so `wrangler types` keeps the secrets required. Gate caches dependencies only in jobs that install (`build`, `e2e`, `repo`, and cache-warm), with explicit and automatic caching disabled in `checks` and the verdict job.

**Secrets:** `standards.json` `"secrets": {"required": [...], "store": ...}` plus the wrangler config's own `secrets.required`. `1password` (our accounts): every staging and Preview deploy re-supplies them with `--secrets-file` (workers-sdk #15942 drops a Preview's secrets on redeploy), read from the client's vault (Builds variable `OP_VAULT`, item `staging`, one field per secret) through the org's CI-only service account (Builds secret `OP_SERVICE_ACCOUNT_TOKEN`) and a checksum-pinned 1Password CLI; values are never printed or left on disk, and without those settings the deploy warns and keeps what the Worker has. `secrets_store` (a client-owned account): `--check` requires a `secrets_store_secrets` binding for each in all three sections, and nothing is re-supplied. After each deploy the staging Worker, the Preview and the production Worker must list every required secret, or the build fails naming it (set production's once with `wrangler secret put`).

**PR Preview clean-up:** `std-preview-cleanup.yml` deletes a pull request's Preview when it closes (merged or not), and a weekly sweep deletes those of pull requests closed in the last 30 days that no open pull request's branch uses (never `staging`). It reads a previews-scoped Cloudflare token and the account id at runtime from the overlay's `"preview": {"cleanup": {"token_ref": "op://…", "account_ref": "op://…"}}` (org secret `OP_SERVICE_ACCOUNT_TOKEN`, the CI-only service account); without it the workflow only posts a notice. Previews of branches that never had a pull request are not swept.

**Portal pass:** with the overlay's `"portal": {"issuer": "https://portal.example.com", "jwks_url": "https://portal.example.com/.well-known/jwks.json"}`, every staging and Preview Worker refuses any request without a short-lived pass the org's client portal signed. The Worker calls the managed module first: `import { portalPass } from "<path>/scripts/agent/portal-pass.mjs"; const denied = await portalPass(request, env); if (denied) return denied;` (with assets, `assets.run_worker_first: true`). Vars: top-level `ENVIRONMENT: "production"` (production never checks); `env.staging.vars` and `previews.vars` set a non-production `ENVIRONMENT`, `PORTAL_AUD` (`<name>-staging`, and `<name>` for Previews), `PORTAL_ISSUER` and `PORTAL_JWKS_URL`. `--check` requires all of that only while `portal` is set; until then sites keep their current gate.
- **The pass:** a JWT signed with Ed25519: header `alg: "EdDSA"` and `kid`; the key comes from the JWKS (`kty: OKP`, `crv: Ed25519`), cached 10 minutes and refetched at most once a minute on an unknown kid.
- **Claims:** `iss` = the portal origin; `aud` (string or list) names the Worker; `sub` = `user:<id>`, `agent:<name>` or `test:<owner/repo>#<run>`; `exp − iat` ≤ 900 s, 60 s clock skew.
- **Transport:** `Authorization: Bearer`, the `__Host-portal_pass` cookie, or a one-time `?portal_pass=` that redirects to the same URL without it and sets the cookie (HttpOnly; Secure; SameSite=None; Path=/).
- **Failure:** an empty 401 with `WWW-Authenticate: Bearer realm="portal"`; a staging Worker missing its portal settings fails closed. The portal issues passes, agents' and test runs' included; the engine only verifies.

### Rollback-safe releases (expand/contract)

In 0.7.4, `checks` and `scripts/agent/setup.sh --check` compare production Wrangler configs and new D1 migrations against the PR base. Rolling production back deploys the previous Worker version, so its schema, Durable Object classes and bindings must still work. Draft PRs warn; ready PRs and merge queues fail. Locally the base is the merge base with `origin/HEAD`, `origin/main` or `main`; set `ROLLBACK_BASE=<commit>` to select it explicitly. CI passes the PR base and draft status from gate's plan step, including dispatch re-gates. In 0.7.5, missing selected commits are fetched from origin at depth one without tags. With no inferred base, the guard fetches origin’s default branch using `git fetch --no-tags --depth=1 origin HEAD`. Unavailable comparison data with any remote fails even in drafts and names the attempted recovery. Only a repository with no git remotes may skip an unavailable comparison with a NOTE.

Split into expand now, contract in a later release: add tables and nullable columns (or columns with non-null defaults), deploy code that stops using the old objects, then contract after that code is the previous release. The guard requires contracts for DROP VIEW/INDEX/TRIGGER, unique indexes on existing tables, triggers affecting existing tables (including their bodies), SQL it cannot positively classify as expand-only, and rejects DROP TABLE/COLUMN, table/column RENAME, unsupported ALTER type/constraint changes and DELETE, UPDATE and REPLACE rewrites of existing data. Historical table and column renames retain existing targets; a CREATE TABLE targeting an existing table never proves a column fresh. Plain INSERTs into tables with schema-level ON CONFLICT REPLACE require a contract; explicit INSERT OR IGNORE/ABORT/FAIL/ROLLBACK and ON CONFLICT DO NOTHING seeds are non-rewriting, while DO UPDATE requires a contract. Updates to columns or tables introduced by the new migrations are expand steps; every top-level assignment is checked even when its value contains a subquery with WHERE. Historical migration edits or removals fail; add a new file. Migration directories come from each production D1 binding's `migrations_dir` (or config-level value), defaulting to `migrations`, relative to its Wrangler config (including `standards.json` `release_workers`); JSON, JSONC and TOML are supported. Production builds of both revisions are compared, including adapter-generated configs, bindings, migration directories and emitted SQL history; the comparison also runs after gate builds. The base builds in a temporary checkout, reusing dependencies only for non-workspace builds with matching manifests and lockfiles; otherwise its dependencies are installed. For pnpm/yarn, installation and both revision builds use temporary npx Corepack bootstrapping without global package-manager shims. An unavailable build fails closed.

A deliberate SQL contract requires a header such as `-- contract: previous release stopped using users.old; issue #123` (an issue/PR number or GitHub issue/PR URL) and a repo-owned `rollback-contracts.json` list of exact affected objects per migration:

```json
{ "migrations/0003_contract.sql": ["users.old"] }
```

Use `users` for table deletion/rename, DELETE/UPDATE rewrites, unique indexes or triggers on that table (also list existing objects rewritten by a trigger body); use the view/index/trigger name for its deletion, and `users.old` for column changes. Unclassified statements name their first argument (or `<statement>` when absent) in the finding; that exact object needs a contract. Accepted contracts print a note: verify that the previous release already stopped using every listed object. The guard cannot prove runtime usage; the linked issue or PR must supply that evidence. DO class export removals/renames and new `deleted_classes`/`renamed_classes` migrations fail while the class is bound by either release, including bindings in other production Workers resolved by `script_name` and `class_name`. Removed production D1/KV/R2/queue/service/DO bindings fail; keep them through the rollback window. Staging and preview binding changes do not count as production removals.

## Cloud configuration

With the overlay's `"cloud_env": { "action": "<owner>/<repo>[/<path>]@<ref>", "token_ref": "op://<vault>/<item>/<field>" }`, apply ships `.github/workflows/std-cloud-env.yml` (the action rendered into it) to each repository that has a `cloud-env.json`, and retires it when the file goes. The action takes `args` and runs the org's cloud-env CLI on `cloud-env.json`; a private action repository must allow access from the organization's repositories. A `cloud-env.json` change on a pull request runs the check with `--check --offline` and no token. A push to `main` reads the Cloudflare token through `1password/load-secrets-action` (org secret `OP_SERVICE_ACCOUNT_TOKEN`, a CI-only service account) and applies. A manual run checks, and on `main` also applies, which onboards a `cloud-env.json` that predates the workflow. With `token_ref` `null` the apply step is skipped with a notice. The workflow is not a required check.

## Session start

The SessionStart hook runs `scripts/agent/setup.sh --check` (which also warns about a `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in a folder above the repository, up to `$HOME`: Claude Code then skips AGENTS.md): the offline check, then (only after it passes, never in CI) `cleanup.mjs`, which removes local branches and worktrees of merged work. One batched GitHub call asks which branches' pull requests merged (squash merges look unmerged to git); a branch goes, with its worktree, only when its PR merged in this repository at its local tip or a later commit and the worktree has no changes, untracked or ignored files (ignored ones only inside regenerable directories: `node_modules`, `dist`, `build`, `.next`, `.turbo`, `.cache`, `coverage`, `test-results`, `playwright-report`), is unlocked, not the main one or the session's own, and not under `~/.codex/worktrees`, `~/.t3/worktrees` or `.claude/worktrees`. Anything unsure stays; a network or auth failure removes nothing within a 1.5-second timeout; one line names what went. Also outside CI, whatever the check's result, `fresh.mjs` warns on stdout (where the agent sees it) when the session is on the default branch: behind `origin/<default>` (it fetches that one branch within a 3-second timeout, `STD_FRESH_TIMEOUT_MS`; unreachable is one notice), or in the primary checkout rather than a linked worktree. It never moves HEAD, touches the working tree or changes the exit status. Cloud setup (`setup.sh` with no arguments) installs tools and dependencies best-effort and exits with the check's status.

## One-time, per person

- Claude: bypass cannot be set from a repository. Set `permissions.defaultMode: "bypassPermissions"` in `~/.claude/settings.json` (or run `claude --dangerously-skip-permissions` once and accept the dialog). `setup.sh --check` warns while it is off.
- Codex: trust each repository (accept the prompt, or add `[projects."<path>"] trust_level = "trusted"`). Until then Codex ignores the repo's bypass and rules; `setup.sh --check` warns with the fix.
- Deny rules bind even under bypass: agents cannot read secret files or run `op`, and cannot force-push. Repo scripts that need a secret (for example `sentry-setup`) read it themselves.

Models: repositories never pin a model or effort; each person's app (or the org launcher) decides. Apply removes any pin from the root `.claude/settings.json` and `.codex/config.toml` (`scripts/agent/pins.mjs` lists the keys), and `--check` fails on one.

## Gotchas

- The `deploy` module runs `wrangler deploy` only; a Worker with D1 must run `wrangler d1 migrations apply <db> --remote` before it.

- In issues and comments write "the Codex mention", never the literal handle: any comment containing it starts a paid task, even on a closed issue.
