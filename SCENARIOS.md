# Engine scenarios

Each scenario reproduces a failure that actually happened or a rule the owners stated, and runs through a real entry point: `apply` on a fixture repository, then `scripts/agent/setup.sh --check`, a `gate` step, the PR helper, or `sync` against a GitHub stand-in. `test/run.sh` prints `ok <id>` or `FAIL <id>` for each and fails if any id below is missing. Ids are stable; a retired id stays listed as retired.

## Gate and evidence

- **`gate-local-runs-ci-steps`**: the local gate runs setup, instructions, secrets, syntax, install, typecheck, build, repo checks and the same e2e command in order, and reports HEAD and each result. A failing repo check stops the tail.
- **`gate-local-starts-and-stops-worker`**: the real fixture Worker starts with repo Wrangler and local bindings, readiness is bounded and it stops after success, failure or interruption; an existing server is refused.
- **`gate-local-e2e-against-local-url`**: the fixture suite makes HTTP calls through the real Worker to local KV using both base URL variables. A failing e2e returns non-zero from the local gate.
- **`gate-local-no-secrets`**: the full fixture gate passes with no Cloudflare credentials or vault access, ignoring inherited remote preview context; its ignored `.dev.vars` holds only dummy values. Legacy home OAuth caches are unreadable in Wrangler build.command and the served Worker; credential-bearing `.env*` files are refused before children (Wrangler 4.148 overwrites empty env values). macOS and Linux use checksum-pinned platform builds of the same scanner.
- **`gate-local-base-required`**: a feature-only checkout without any default ref fails before instructions or secrets; an explicit missing base fails, while an explicit commit or origin/main with a distinct feature commit works. Explicit HEAD and automatic refs equal to or containing HEAD fail before children. Review incident: falling back to HEAD scanned an empty range.
- **`gate-local-remote-refused`**: only direct Wrangler dev invocations are accepted, --local is enforced, conflicting/remote flags and wrappers fail, and a selected JSONC config with remote: true bindings fails before startup. Review incident: custom dev commands could reach remote bindings.
- **`gate-local-hup-cleanup`**: SIGHUP during the real Worker e2e stops the detached process group, exits 129 and frees the TCP port. Review incident: SIGHUP orphaned the Worker.
- **`gate-local-no-worker`**: in a repository with no root Wrangler config and no `release_workers`, `gate.mjs local` needs no `local` setting: the `worker` step reports `SKIP (no Worker)`, the other steps run, and the pass record that `pr.sh ready` reads is written when they pass; a repository with a Wrangler config still starts its Worker, and `"local": false` still opts out. Stated rule: agents in Worker-less repositories can mark pull requests ready without hand-adding settings.

- **`gate-local-opt-out`**: `local: false` skips only server startup, preserving the same e2e suite, and survives apply. Invalid local shapes, non-loopback URLs and escaping readiness paths fail the offline check.

- **`gate-fails-without-e2e`**: a repository with no end-to-end suite fails `gate` (the suite was once skipped silently while `gate` went green). The workflow has one job named `gate` (the required check), which aggregates the checks job and the parallel tail that carries every step.
- **`setup-installs-repo-playwright`**: `setup.sh` installs the Chromium browser with the repository's own Playwright (`node_modules/.bin/playwright`), never through npx, and says so when the package is declared but not installed (npm 6's npx read `--no playwright` as an option value and installed nothing).
- **`e2e-opt-out-honoured`**: `"e2e": false` in `standards.json` skips the e2e step with a warning (even where a suite exists), passes `--check`, and re-applying the pack keeps it.
- **`e2e-false-skips-preview`**: `"e2e": false` also skips the preview step, so a repository whose Workers Builds run on every pull request but publish no preview URLs and have no e2e suite passes `gate`; without it the same repository fails for the missing build. Incident: such an operating repository was held on the previous release.
- **`preview-url-from-bot-table`**: the preview URL is the "Preview URL" (or "Deployment URL") cell of the Cloudflare bot table row whose commit is the head, read by the table's header row in a markdown or an HTML table, else the `Preview URL: <url> (commit <sha>)` line naming the head; never a link to the Cloudflare dashboard, and "No Preview URL", a table without the column (a production deploy comment) and a row for another commit mean none, so gate fails. Bodies are real bot comments from `test/fixtures/cf-comments`, made neutral. Incident: gate took the first link on the head's row, the build's "View logs" dashboard link, and tested it.
- **`ui-paths-evidence-required`**: a pull request changing a UI path (markup, styles, components, .docx, .pptx) fails without an accepted evidence comment and passes with one. A rename counts by both paths, so moving a UI file out of a UI path needs evidence too.
- **`evidence-comment-author-or-app`**: an evidence comment by anyone but the PR author, an app or an overlay-trusted login is rejected (a forged comment once passed).
- **`evidence-images-pinned-resolving`**: every evidence image must be in this repository at a 40-hex commit and exist there, as four distinct image files (before and after at 400 and 1280px); the PR helper posts images that way and re-posting updates one comment.
- **`evidence-document-pages`**: a PR whose UI paths are all documents (.docx, .pptx and similar) accepts before and after page images (`before-N`, `after-N`) with at least one page in both; a PR that also changes web UI needs the 400 and 1280px set and the pages.
- **`ui-paths-repo-override`**: `standards.json` `ui_paths` replaces the default globs, and `{ "ignore": [...] }` keeps them while exempting paths (release notes generated upstream once tripped the evidence gate).
- **`ui-paths-empty-warns`**: an explicit `ui_paths: []` turns the evidence gate off, and `--check` warns naming tracked files the defaults would cover.
- **`test-quality-warns`**: `--check` warns, never fails, with file:line on `setCPUThrottlingRate`, `test.retries`, `retries:` in a Playwright config and `waitForTimeout` under tests; comments and non-test files stay silent; `std-implement` and `std-autoreview` carry the rules and the reviewer rejects violations.
- **`no-evidence-on-main`**: tracked `.evidence/` fails `--check` (gate's standards step); the PR helper leaves no `.evidence/` on the branch tip after posting.

### Review (the pull request's conversation: `scripts/agent/review.mjs`, exported as `repo-standards/review`)

- **`codex-verdict-required`**: the review rule passes a non-draft PR only when the Codex summary shows the current head as Completed (after the head's push and any base edit) and every Codex thread is resolved; before that it is pending for 20 minutes, then fails ("no Codex verdict … request a review"); drafts are not evaluated; repos without Codex reviews pass; the sync's fallback PRs get no exemption (anyone with write access can push to their branch). The evidence cases above and the promotion cases below go through the same rule.
- **`review-rule-reads-base`**: the rule reads its settings from the current base branch commit (a pull request cannot bring its own; GitHub can retain an older `base.sha`, so the branch is resolved), even when the head is this repository's default branch.
- **`gate-code-only`**: only code changes start gate (a pull request's commits, the merge queue, the launcher's dispatch after a base change); comments, reviews, edits and pushes start nothing, no re-run wrapper ships, and gate has no step that reads the conversation (no `review` subcommand; the rulesets require resolved threads instead). Incident: every Codex event and thread reply rebuilt the site (759 billed minutes of review re-runs in one org in a day; 241 minutes in 138 runs on one repo in the other; 104 minutes from preview-bot comments).

### CI minutes (each reproduces a measured cost from the Sep 27 Actions audit)

- **`gate-no-push-regate`**: pushes start no gate run, neither to main or staging (the tree was gated as a PR) nor pack landings. Incident: 442 billed minutes of post-merge gates.
- **`gate-ignores-body-edits`**: a title or body edit starts no gate run; after a base change the launcher dispatches gate on the PR's fresh merge ref.
- **`gate-parallel-tail`**: the one required check, the job `gate`, needs the checks job (plan, standards, instructions, secrets, syntax) and the one `test` job (install, browsers, typecheck, build, `gate.local.sh`, preview, e2e); it passes only when each succeeded, or when the test job was skipped because the checks planned a draft's cheap gate; a failure, a cancellation, an unplanned skip or a missing job fails it. `test` and `gate` check out the exact tree the checks job tested (a re-gate's merge ref can move meanwhile), and `gate` sets up its own Node. Every job's timeout is the overlay's `gate.timeout_minutes` (default 30). Incident: a repository's full single-job gate ran about 14m50s against a 15-minute cap and was cut off.
- **`skip-never-greens-gate`**: the required gate job's only job-level `if` is `always() && !cancelled()` so it never skips (a skipped job reports success and could mask a red gate on the same head); a dispatch re-gate plans the pull request it names (full gate), never "not a pull request".
- **`draft-cheap-ready-full`**: drafts are not gated; the cheap path (the check, the secret scan and a syntax pass that fails a broken script and skips workflows where PyYAML is missing); `ready_for_review` runs the full one.
- **`gate-browser-cache`**: the test job installs dependencies with `--no-browsers`, then restore `~/.cache/ms-playwright` with a SHA-pinned `actions/cache/restore` named by `gate.mjs playwright` (the repo's exact Playwright version plus this run's sorted browsers; none, and no cache or browser step, without Playwright), then run `install --browsers-only`: `playwright install` for the browsers (a no-op on a hit) and `install-deps` unless a Chromium-only run passes an equivalent of Playwright's own host validation (`ldd` over every executable and shared library in `chrome-linux`, a missing bundled `.so` included); Firefox and WebKit always run `install-deps` (their libraries load through paths and dlopen that the scan cannot see), and `--with-deps` is gone. `std-cache-warm.yml` seeds the same caches on the default branch, since pull requests read only its caches. Incident: every e2e and repo job ran apt update, a deps install and a browser download, up to 4.2 minutes each.
- **`gate-never-writes-cache`**: `std-gate.yml` only restores caches (`actions/cache/restore`, and `setup-node` with `package-manager-cache: false`), never saves one: a `workflow_dispatch` re-gate on the default branch runs a pull request's merge tree, so a saved cache would be seeded by that tree and trusted by every later run. Only `std-cache-warm.yml` (pushes to main, no pull request code, no `workflow_dispatch`) saves the dependency and browser caches, under the same names the gate restores. Incident: review of the browser cache change.
- **`gate-edit-cheap`**: a description or title edit (`action: edited`) plans the cheap path, so only the checks job runs; it fails when the head's latest `gate` run is red or unfinished, so it cannot turn a failing or running full gate green, and it has its own concurrency group (`-edit`), so it cannot cancel the full gate. The workflow carries no `edited` trigger yet (`gate-ignores-body-edits`); adding one is safe.
- **`e2e-chromium-default`**: gate installs and runs Chromium only, on every pull request (one from the default branch into `main` included); a repository's extra browsers run on main in the release check (`release-browsers-on-main`), and only for projects the Playwright config defines; a config whose projects are named otherwise is refused (without `--project` Playwright runs them all); a package script running `playwright test` gets the same selection. Incident: three-browser suites ran on every PR.
- **`cache-only-with-install`**: rendered npm and pnpm workflows disable explicit and automatic package-manager caching in checks and verdict jobs, which install nothing; the test job and cache-warm retain caches with installs. Incident: the pnpm checks job failed in setup-node post-cache because no store was created.
- **`dependency-cache-by-lockfile`**: gate and `std-cache-warm.yml` cache the lockfile's package manager (npm, pnpm, yarn; pnpm and yarn through corepack, and no cache rather than a failed step when that fails), with the same step in both, and the warm-up fires on any of the three lockfiles. Incident: pnpm repositories never warmed or hit a cache.
- **`e2e-uses-preview-url`**: with a Workers Builds check run on the head, e2e runs against the preview URL from the Cloudflare comment for that commit; a red Cloudflare build fails gate; with none, e2e runs locally. The job has `checks: read`, which reading check runs needs.
- **`preview-must-pass`**: where the repository has Workers Builds (the check is on its base branch tip), gate waits for the head's build and fails when it is missing, still running at the wait limit, or anything but success; e2e runs against that build's preview URL, and a passed build with no URL for the commit in the Cloudflare comment fails too (never a local run); a build Cloudflare skipped is the one case without a preview; repositories without Workers Builds, or with `e2e.preview: false`, run e2e locally.
- **`gate-instructions-guard`**: gate's `instructions` step fails a pull request that changes an instruction file at any depth or the managed CODEOWNERS block, whoever opened it, the repository owner's own login included. Instruction files are `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `CLAUDE.local.md`, and `.claude/agents|commands|rules/`, counted by both paths of a rename. The block counts when it is edited, dropped, or replaced by a symlink; a repo line above it, `.claude/settings.json` and code pass. The step runs in draft and full gates alike, right after the standards check. Stated rule: agents never write instruction files; the launcher's instructions-guard needed an App permission change and missed PRs opened under the owner's own login, which skip code-owner review.
- **`gate-instructions-regenerated-block`**: an AGENTS.md change passes the instructions step only when it is exactly what the pack's apply generates at the pull request's head (the template under review rendered over the base file, via standards.json `overlay`, in a repository that carries the engine); a hand edit inside or outside the block, a block edit without the template changing, a regenerated block plus an extra hand line, a pull request that adds or changes the renderer, and one that changes or redirects the overlay are refused: the base commit supplies the renderer, the overlay, standards.json and the template; the pull request supplies exactly one file, template/AGENTS.block.md, read as plain text, so none of its JavaScript runs (top-level code in its pins.mjs or staging.mjs is inert), and AGENTS.md and the block file must be regular git blobs (a symlink is refused). The guard catches honest mistakes; it is not a security boundary against a crafted pull request. The sync and retro exemptions stay. Stated rule: the engine's own dogfooded AGENTS.md follows template changes in the same pull request, with no exemption for the engine repository.

- **`gate-instructions-exempt-sync-retro`**: only the org App's own pull requests from `standards/v*` (sync) or `retro/*` (approved retro) are exempt. The App on another branch, or a person on those branches, fails. A dispatch re-gate reads the author and head ref from the pull request, and a run outside a pull request (merge queue) passes with a notice.
- **`gate-skips-doc-only`**: a pull request whose changes are all non-deployable paths (root Markdown, `docs/`, any `AGENTS.md` or `CLAUDE.md`, `.github` issue and PR templates, `LICENSE`, `.agents/`, `.claude/`, `.codex/`, design-session scratch under `.impeccable/`) skips the preview and e2e steps, saying so and naming the files; one deployable path (code, or Markdown that ships, such as `src/content/` or `public/`) runs both, and a run outside a pull request skips nothing. The diff is the PR's merge commit against its base parent, or the head against the event's base. Incident: Workers on the old preview model never post a preview URL, so every doc-only PR in those repositories failed gate, and each one spent a full e2e run.
- **`e2e-budget-removed`**: the e2e step has no time budget: a suite slower than a leftover `standards.json` `e2e.budget` passes, `--check` warns that the setting is ignored, an overlay that still sets `gate.budget` loads with one notice saying it was removed (never refused), and `gate_budget` is gone from the defaults. `gate.timeout_minutes` stays as runaway protection only.
- **`quarantine-expires`**: `@quarantine` needs an issue link and an expiry at most 14 days out; an expired one fails `--check`.
- **`no-duplicate-gate-workflows`**: a repository workflow that runs checks on pull requests, or re-tests pushes to the default or integration branch, or a schedule more frequent than daily, fails `--check`; the declared deploy workflow may build on push. Incidents: a duplicate `validate.yml` ran 142 times; a sub-hourly alert poll billed 166 minutes. A push trigger limited to other branches is read where it stands, even when `on:` is not the workflow's first line.
- **`duplicate-check-exception-pinned`**: a repo can keep a named artifact-validation or release guard workflow beside gate only by listing its exact path, SHA256, and nonempty rationale in `standards.json` `duplicate_check_exceptions`; an absent, malformed, stale or changed pin fails `--check`. The exception affects only the duplicate-check rule: job timeouts, schedule frequency, and browser install checks still fail when violated.
- **`jobs-have-timeouts`**: a workflow job without `timeout-minutes` fails `--check` (the default is 360 minutes).
- **`secrets-scan-changes-only`**: the secret scan covers the pull request's own commits, including on a dispatch re-gate of the merge ref, so an old leak already on the base does not fail it.

## One-branch releases

- **`release-generated-builds`**: adapter-generated flattened Wrangler configs select staging with `CLOUDFLARE_ENV=staging`, then build production separately with it unset before versions upload. Incident: an adapter ignored deploy-time `--env staging` and deployed production.
- **`release-generated-guard`**: release resolves the adapter redirect and aborts before any Wrangler command when the target is production rather than exactly `<name>-staging`.
- **`release-production-route-guard`**: staging cannot bind a production hostname through a route or custom domain, even with a different path or scheme.
- **`release-staging-output`**: Wrangler must confirm the staging Worker name; mismatched output aborts production upload.
- **`release-plain-config`**: plain JSONC staging applies its environment and pins the checked config and staging name before deploying.
- **`release-generated-check`**: the offline check requires exactly `<name>-staging`, and it and a fresh CI build reject redirected builds that ignore `CLOUDFLARE_ENV` and accepts builds that restore production after the staging probe. Quiet build failures suppress all build output, including undeclared database credentials, and name the local reproduction command, environment selection, package-manager bootstrap and exit status or signal.

- **`review-no-promotions`**: the review rule has no promotion path: a pull request from the default branch into another branch is judged like any other (a UI change needs its evidence comment; a person's approval is no substitute, since code-owner approval on `main` is the rulesets' business).

- **`release-browsers-on-main`**: a repository's extra browsers (`standards.json` `e2e.browsers`, or the overlay's `e2e.release_browsers`) run on main, not on pull requests: apply ships `std-release-check.yml` (pushes to main and manual runs) only where some are named and the repository has not opted out with `"e2e": false`, `--check` then requires an https `staging_url` (not under `"e2e": false`, which ships no release check), and `gate.mjs release` waits for the commit's Workers Builds (failing on a failed or unfinished build; where the parent commit had a build, a check not created yet is waited for within the window, not taken as absent) and hands Chromium, the extra browsers and the staging URL to the install, e2e and repo-check steps; the overlay's old `e2e.promotion_browsers` is refused. Stated rule: the extra browsers test the build staging runs, before a person deploys its uploaded production version.

- **`block-visuals-and-deploys`**: the shared instruction block carries the visuals rule (screenshots and video are for the people reviewing the PR, never a test, never compared; video when it moves, before/after when static), the no-per-repo-exceptions rule and the Cloudflare deploys rule, and not the old "Visual change" line.

- **`agents-md-block-only`**: the overlay setting `agents_md: "block-only"` makes apply write AGENTS.md as exactly the managed block (anything outside it removed) and `--check` fail on content before or after it; without the setting repo content around the block survives apply and passes `--check`; any other value is refused. Stated rule: an organization whose AGENTS.md is the standards block only.

- **`release-check-every-worker`**: `std-release-check.yml` ships to every repository with a root Worker config and an https `staging_url` (not to one lacking either, unless it names extra browsers; `"e2e": false` opts out); its job is the check-run `release-check`, it is dispatched with a sha (never started by a push, check-run or schedule), one run per commit (concurrency by sha), and runs the full suite (e2e and `gate.local.sh`, `GATE_SELECT=full`). Stated rule: the full suite runs once, on the merge commit, against staging, before the production deploy.

- **`release-check-managed-only`**: `--check` accepts the managed release check but still rejects any repo-owned workflow that tests on push to main (whatever its name) and a hand-edited managed copy.

- **`release-check-notice`**: a repository with no release check (no Worker, or no `staging_url`) gets a `--check` notice naming the reason, not a failure.

- **`release-version-tagged`**: every production `versions upload` carries the full commit SHA as `--tag` (`WORKERS_CI_COMMIT_SHA`, else `GITHUB_SHA`; with neither it warns the version is untagged), and `--check` warns where a repo's own scripts or workflows document `versions upload` without `--tag`. Stated rule: the portal ties a version to its `release-check` through the tag.

- **`release-check-trigger`**: the release check runs only before a production promotion, the same for every repository: `std-release-check.yml` has `workflow_dispatch` with a required `sha` input and no `check_run`, push, pull-request or schedule trigger and no job condition; the commit under test is that `sha`, never `GITHUB_SHA`; concurrency is per sha; the verdict is posted as the check-run `release-check` on that commit; a repository with no Workers Builds fails it rather than guessing. Stated rule: the full gate runs only before a production promotion (about 250 minutes a day of release checks for never-promoted commits are gone).

- **`release-check-provenance`**: a consumer accepts a `release-check` only through `release.mjs verify-release-check <sha>`: the check-run is successful, from GitHub Actions, and its `external_id` is the id of a workflow run of `.github/workflows/std-release-check.yml` with event workflow_dispatch, `head_branch` the default branch, display_title `release-check <sha>` and conclusion success; a forged check-run whose external_id points at a real run for another sha, a push or feature-branch run, another workflow's run, another App's check-run, and a check-run with no run id are refused; the workflow's `pre` job refuses a dispatch from any ref but the default branch.

- **`release-check-trusted-steps`**: the `release-check` verdict is written only by trusted steps: the workflow has three jobs; `pre` and `post` run the default branch's workflow and scripts (they check out the default branch, never the sha) and alone hold `checks: write` and `actions: write`; the `suite` job is the only one that checks out the sha and holds `contents: read` only, with no token or secret in any of its steps; the sha is shown to be an ancestor of the default branch in plain shell, before any script runs, and an off-main sha is refused by that step alone.

- **`release-check-dispatch-contract`**: what the portal relies on: `sha` is a required exact 40-lowercase-hex `workflow_dispatch` input (anything else fails fast with a plain error, before checkout); the job checks out exactly that sha and fails plainly, creating no verdict, when the default branch does not contain it; a `release-check` check-run is created `in_progress` on that sha when the job starts (its `external_id` is the workflow run id, `details_url` the run's URL) and completed once by the report step, computed at report time: success only if pre, the suite and the supersession check all succeeded, cancelled if anything was cancelled, failure otherwise (including a green suite whose supersession check failed on an API 503, a skipped suite, and a failed pre); a superseded or nothing-to-certify run completes it `neutral` with the reason and a "not a pass" summary and the report step leaves it; `run-name` is `release-check <sha>`.

- **`release-check-staging-superseded`**: a release check certifies a commit only through its own staging Workers Builds check (completed and successful, waited for without a time cap when late); before and after the suite, any later commit on the default branch (each one, so a change and its revert both count) whose staging build is running or completed with any conclusion but skipped or neutral (a failed build may already have deployed staging) supersedes the run; only the Cloudflare App's checks count, so a same-named check from another App is ignored. A superseded or nothing-to-certify run cancels itself, force-cancels if the runner is not interrupted, and fails closed if that too fails; it never passes. The post-suite step also runs after a failing suite. Stated rule: staging serves the newest build that deployed, so a run never certifies a commit whose deployment it did not test.

- **`release-check-a11y-contract`**: `RELEASE_CHECK=1` is set by the release check's e2e (`gate.mjs e2e --release`) and repo-check steps and never by the pull-request gate: a failing `@a11y`-style test (one that runs only when `RELEASE_CHECK=1`) fails the release run, and the PR gate's e2e and repo checks clear the variable even when inherited, so it does not run. Stated rule: axe scans run once, in the release check.

- **`release-check-full-suite`**: a release run (`gate.mjs e2e --release`, `GATE_SELECT=full`) runs every Playwright project, including a non-browser one, with no file filter and no time cap (no `PW_GLOBAL_TIMEOUT`, no subprocess timeout), while the pull-request gate stays on Chromium.

- **`release-check-skips-docs`**: a release check certifies only what the authenticated Builds results on the commit show: builds all skipped (or neutral) mean nothing to certify and cancel the run, while any successful build certifies the commit even when its last commit changed only non-deployable paths (a source-then-docs push); later steps are skipped through a step output rather than a job-level `if`. Stated rule: no CI run when nothing deployable changed.

## Staging environment and PR Previews (stated rule: staging is a Wrangler environment, a separate Worker with its own data, queues, Workflows, cron and keys; Previews point at staging; nothing outside production reaches production. Incident: Worker Previews share Workflows, service bindings, queue consumers and cron with production)

- **`staging-env-required`**: a repository's root wrangler config (JSON or JSONC) fails `--check` without `env.staging`; a config with data bindings is never migrated automatically (the fix names the staging resources to create). The staging Worker may not take the production name, inherit or claim a production route (string or object; a Preview hostname counts unless its production traffic is disabled), or leave out any binding kind or var production declares (neither is inherited). A TOML config gets a warning that it is not checked. `standards.json` `"staging": false` opts a Worker out of the environment, not out of the Preview checks.
- **`staging-brochure-migrated`**: apply gives a Worker with no data bindings (a brochure site) its `env.staging` (its vars with `SENTRY_ENVIRONMENT`/`ENVIRONMENT` set to `staging`, its non-data bindings, `routes: []`, `workers_dev: true`, `preview_urls: false`) and, when missing, a `previews` block, by inserting text before the structural closing brace (not one in a comment): comments and string values (even `", }"`) stay, the result passes `--check` (warning that a workers.dev staging Worker needs the org's Access until the portal gates it), and a second apply changes nothing. So a sync upgrades 0.6.x brochure sites.
- **`staging-no-production-resources`**: `--check` fails when `env.staging` or `previews` names a production D1 id or name, KV id, R2 bucket, queue (produced or consumed), Workflow, or service-binds a production Worker (the Worker itself or one production binds to), and when `previews` carries queue consumers, cron triggers or routes, which never target Previews.
- **`previews-point-at-staging`**: `previews` must exist (Previews inherit nothing) and bind every production data binding by the same name to the resource `env.staging` uses; a missing binding or a different resource fails.
- **`staging-required-secrets-inherited`**: the brochure migration copies top-level secrets.required into env.staging; --check rejects missing or incomplete staging declarations. Incident: wrangler types made required secrets optional, breaking typecheck.
- **`staging-secrets-declared`**: `standards.json` `secrets` is `{required, store: "1password" | "secrets_store"}`; with `secrets_store` (a client-owned account) every required secret (these and the wrangler config's own `secrets.required`) is a `secrets_store_secrets` binding at the top level, in `env.staging` and in `previews`.
- **`release-staging-env`**: the production trigger's command (`release.mjs main`) applies this commit's D1 migrations to staging's own databases, deploys the staging Worker (`wrangler deploy --env staging`), then uploads the production version (`wrangler versions upload`, tagged with the commit and `SENTRY_RELEASE`). A failed deploy uploads nothing. A config without `env.staging` (a 0.6.x repository) gets a warning and deploys the legacy `staging` Preview, so the trigger and the config can switch in either order.
- **`release-secondary-workers`**: standards.json release_workers lists secondary configs; every staging target is checked before any deploy, including against all production routes. Only the primary production versions upload retains Builds override-name and match-tag variables; secondary config commands and builds receive neither. Secondary staging Workers deploy under their own -staging names, and production versions upload under their own names. Incident: a secondary Worker was uploaded as the primary Worker and its Durable Object namespaces broke rollback.
- **`release-secrets-resupplied`**: every staging and Preview deploy gets `--secrets-file`, a mode-600 JSON file in a private temp directory, read from the per-client vault (`OP_VAULT`, item `staging`, one field per secret) with the checksum-pinned 1Password CLI, and removed on every exit. The production upload never gets one. No value is ever printed. Without the vault settings the deploy warns and keeps the Worker's secrets (the post-deploy check still fails a missing one); a missing field fails before any deploy. `store: "secrets_store"` re-supplies nothing. Incident: a Preview drops the secrets set on it when it is redeployed (workers-sdk #15942).
- **`release-cross-account-refused`**: release and `--check` reject staging or secondary account_id values that differ from the primary root account_id, including adapter-generated configs, before any remote command. Matching accounts and inherited staging accounts remain supported. Incident: a name-only staging secret check could reload the production account and query the wrong account; cross-account staging isn't supported yet.
- **`release-staging-secret-target`**: after an Astro staging deploy, secret list uses exactly the guard-approved `<name>-staging` without `--env`; the production versions upload then runs. Incident: Wrangler appended staging twice and stopped the release before upload.
- **`release-staging-bootstrap`**: a missing staging Worker with required secrets deploys with a private secrets file from the configured build source; without one, release stops before production upload and names the one-time `wrangler deploy --env staging --secrets-file <file> --dry-run`, then `wrangler deploy --env staging --secrets-file <file>` bootstrap. Incident: secrets could not be set before the Worker existed.
- **`release-secret-check`**: after each deploy, the staging Worker, the Preview and the production Worker must list every required secret (names only; the JSON is read even after a banner or warnings). A missing one fails the build and names it, and staging failing stops the production upload. An unreadable list fails too.
- **`preview-slug-parity`**: the Preview name for a branch (`release.mjs slug`) is byte-identical to the live trigger's `tr | tr -cs | cut -c1-30 | sed` pipeline, including trimming after the cut. The deploy and the clean-up share this one function. Stated risk: a clean-up that names Previews differently silently deletes nothing.
- **`preview-cleanup`**: `std-preview-cleanup.yml` ships only to a repository with a root wrangler config. It runs when a pull request closes, merged or not, and on one weekly cron. The Cloudflare token and account come at runtime from the overlay's `preview.cleanup` 1Password refs through the pinned load-secrets action, never a GitHub secret; without them it only posts a notice; a malformed ref is refused. It checks out the default branch's code and settings (never a closed pull request's) before loading any credential. The head ref goes through `env`, never into the script. It deletes the closed pull request's Preview unless an open pull request uses the same Preview name (one already gone is fine; other errors fail). The sweep deletes the Previews of pull requests closed in the last 30 days, except a branch an open pull request uses, fork branches, and `staging`. Stated rule (Cloudflare's documented pattern): delete a PR's Preview when it closes; the oldest Previews are evicted at the per-Worker limit.

## Portal pass (stated rule: staging and previews are never public; clients, agents and test runs carry a portal-signed pass)

- **`portal-pass-verifies`**: apply ships `scripts/agent/portal-pass.mjs` (locked). A staging Worker lets a request through with a valid Ed25519 pass from the portal: in `Authorization: Bearer`, in the `__Host-portal_pass` cookie, or once as `?portal_pass=`. The query form answers with a 302 to the same URL without the parameter and sets the cookie (HttpOnly, Secure, SameSite=None, Path=/, Max-Age = exp − now). `aud` may be a list; `sub` may be `user:`, `agent:` or `test:`. An unknown kid refetches the JWKS once, so a rotated key is accepted, and a second unknown kid within the minute does not refetch; concurrent unknown kids share one reserved refetch.
- **`portal-pass-fail-closed`**: each of these gets an empty 401 with `WWW-Authenticate: Bearer realm="portal"` and `X-Robots-Tag: noindex` (so gate's preview noindex probe passes on a gated Worker): no pass; an expired pass, one living longer than 900 s, or one issued in the future (beyond 60 s skew); a wrong `aud`, `iss` or malformed `sub`; `alg` other than `EdDSA` (including `none`), an unknown kid, a different key under a known kid, or a tampered payload; a garbage cookie or a bad query pass; a staging Worker missing `PORTAL_AUD`, `PORTAL_ISSUER` or `PORTAL_JWKS_URL`.
- **`portal-pass-production-open`**: with `ENVIRONMENT` exactly `"production"`, the module never checks and never fetches the JWKS. A near miss such as `"Production"` is still gated.
- **`portal-pass-shared-load`**: concurrent cold requests with valid and forged unknown kids share one JWKS fetch; valid passes proceed and forged passes in that burst get 401 without a second fetch.
- **`portal-pass-load-failure-cache`**: HTTP and malformed-JSON JWKS failures are cached for one minute. Concurrent and sequential forged requests get empty 401s with one fetch; a valid pass is still refused at 59 seconds and succeeds after expiry with one recovery fetch. Still-fresh cached keys remain usable during a pending or failed unknown-kid refetch.
- **`portal-pass-wired`**: with the overlay's `portal` (`issuer` an https origin, `jwks_url` https; anything else is refused), `--check` requires top-level `vars.ENVIRONMENT` `"production"`, `env.staging.vars` and `previews.vars` with a non-production `ENVIRONMENT`, `PORTAL_AUD` (`<name>-staging`, and the production name for Previews), `PORTAL_ISSUER` and `PORTAL_JWKS_URL` from the overlay, a Worker `main` with `assets.run_worker_first`, and a Worker source that imports the module and calls `portalPass(`; apply's brochure migration writes those vars. Without `portal` nothing is asked and sites keep their current gate.

Retired in 0.6.0 with the staged flow: `promote-no-ui-auto`, `promote-ui-needs-human-approval`, `promote-approval-then-merges`, `promote-stale-approval-rejected`, `promotion-not-strict`, `engine-org-flow-property`.

## Pull requests and sync

- **`pr-open-verified`**: the PR helper sends nothing on a dry run, refuses a branch that is not on GitHub, reuses the open PR, and prints a URL only after reading the PR back.
- **`pr-status-done`**: `DONE` only when the PR is open or merged, closes an issue, `gate` is green on the head SHA, and every review thread is resolved (the org rulesets require it); an unreadable thread list is not DONE.
- **`review-round-drafts`**: `pr.sh review-round <pr> "<why>"` converts a ready PR back to draft and records why in one marked comment; `pr.sh ready <pr>` marks it ready only when `gate.mjs local` passed on the pushed, clean head (the pass record is `<git-dir>/std-local-gate`, written by a fully passing local gate and cleared at the start of each run); a refused toggle is an error; `ready` refuses outright inside GitHub Actions, whatever token variable is set (a flip there would not start the full gate); a head that moves during the toggle puts the PR back in draft and fails; tracked changes or non-ignored untracked files (even with `status.showUntrackedFiles=no`), before or after the run, mean no pass record. std-babysit and std-file-pr tell agents to fix in draft. Evidence: -ca spent 2,765 min in 14 days on review-round pushes to ready PRs.
- **`pr-resolve-thread`**: `pr.sh resolve <pr> <comment-id>` resolves only the review thread holding that comment, following thread and comment pages and matching REST ids past GraphQL's Int (`fullDatabaseId`), and fails naming an id no thread holds.
- **`sync-lands-without-gate`**: a pack landing runs no gate (the engine's own CI is the release gate): sync commits on the default head, checks the tree offline, and fast-forwards the default branch with no branch, PR or workflow run. The default branch moving first costs one re-apply, then it lands. A repository still on the retired staged flow, by its `standards.json` or by the org's `flow` property, gets a PR for a person naming the migration instead of a landing. Incident: each fleet roll ran every repository's gate twice (about 60 billed minutes).
- **`release-subdir-worker`**: a Workers Builds trigger whose root directory is `workers/<name>` runs `release.mjs main|preview` for that directory's own Wrangler config (no root config needed): the staging deploy, the production `versions upload` tagged with the commit, previews; `standards.json` is still the repository's; from the repository root, with no config there, it refuses.

- **`release-supporting-workers-first`**: `release_workers` deploy before the primary, in their listed order, for the staging deploy and the production upload (the primary binds Durable Objects and Workflows that live on them, so a new class must exist before the primary's deploy needs it).

- **`release-do-migration`**: a commit that adds a Durable Object migration tag to a Worker's config records it on that Worker's uploaded production version (tag and message: "carries Durable Object migration <tags>: go live with release.mjs promote <sha>"), staging applies it through its normal deploy, and a commit with no new tag is not annotated.

- **`release-promote`**: `release.mjs promote <sha>` makes the commit's uploaded version live: a version deploy for one that carries no migration; for one that carries a Durable Object migration, a full `wrangler deploy` of that exact commit (refused unless it is checked out); no uploaded version tagged with the sha, or a short sha, is refused.

- **`release-sentry`**: with the SENTRY_AUTH_TOKEN build secret and the DSN `sentry-setup` commits in the Worker config, the main release creates the Sentry release for the commit (org from pack.json, project from the DSN's project id) and uploads source maps when sentry-cli and a build output directory exist; without the token it logs one notice; a repository without the DSN is skipped; none of these is an error.

- **`sync-includes-standards-repo`**: sync applies the pack to the overlay's own standards repository like every other repository (only `fleet.exclude` leaves a repository out); a pin pull request there changes only the overlay, and the sync App lands the repository's managed files. Stated rule: no per-repo exceptions.

- **`sync-lists-off-fleet`**: a fleet run lists each organization repository with no `standards.json` in the compliance issue as "not in fleet" and writes nothing to it; excluded, archived, other-pack and other-org repositories stay off the table. Incident: repositories outside the standards were skipped silently, so nobody saw they were missing.
- **`breaking-release-proves-first`**: an engine release marked `breaking` (it can stop a repository's gate or check from passing) syncs nothing on a fleet run (a warning, not a failure) until a person runs `--proven`; it lands on one repository with `--repo`, and landing there is not proof. The proof is recorded in the compliance issue, so the scheduled syncs that follow roll it without the flag.
- **`sync-opens-pr-when-red`**: when the applied tree fails the repository's offline check, sync opens exactly one PR for a person, naming the failures, without auto-merge, and leaves the default branch alone; a PR a person closed for the same content is not reopened. Its body tells a person how to fix it from a fresh branch (only the App may push `standards/v*`).
- **`sync-applies-release`**: sync applies the released overlay with the engine version it pins and refuses a mismatch (an old sync script once ran from a release tag).

## Client sites (profile `client`; incident: each guarded real damage, and a review found nothing enforced them once the copy-pasted AGENTS.md rules were deleted)

- **`client-turnstile-versioned`**: `--check` fails a tracked source file that loads the Turnstile script from any URL but the versioned `/turnstile/v0/api.js` (the unversioned one 404s, so the form never gets a token); the `siteverify` call is not a script and passes; internal repositories are not checked.

- **`client-overflow-clip`**: `--check` fails a CSS rule (in a stylesheet or a component's `<style>`) that is animated on a `view()`/`scroll()` timeline and sets `overflow: hidden` (it freezes the timeline; `overflow: clip` does not), and an `html` rule that makes it a scroll container with `overflow-x` (`hidden`, `auto` or `scroll`; `clip` passes); `overflow: hidden` elsewhere passes. A regex reading of the stylelint rule: it needs no per-repo dependency or install in gate.

- **`client-sentry-four-layers`**: a client site whose Worker runs code (`main` in its wrangler config) and depends on `@sentry/cloudflare` fails `--check` unless all four error layers are present: the Worker wrapper (`withSentry` in the `main` file), the middleware (`captureException` in `src/middleware.*` or under `src/middleware/`), the browser init (`@sentry/browser` with a `tunnel`) and the tunnel's same-origin route; each missing layer is named. When `main` is generated by the build (not a tracked file, such as `dist/_worker.js`), the wrapper is looked for in the tracked source, so a clean checkout never fails for want of a build. A static site (no `main`) and internal repositories are not checked.

- **`client-mail-seam`**: on a client site, mail is sent from exactly one source file, the seam: a file that calls `.send(` on any `send_email` binding the wrangler config declares (JSON(C) at any depth, such as `previews` or an `env`, whatever other fields the entry has; TOML `[[send_email]]` or `[[env.<name>.send_email]]` tables or an inline array), or that imports `cloudflare:email` and calls `.send(`. Passing the binding to the seam is not a send, and neither is a comment or a test's stand-in. The seam must compare the request hostname, or a variable holding it (`const h = url.hostname`, `const { hostname } = url`), with quoted production hosts (`.includes`/`.has` on a host list, or `===`/`!==` against a host), so previews, workers.dev and localhost never mail the client; `--check` fails a second sending file, and a seam that only reads the host (a same-origin check, a log line). Offline: the forms sit behind Turnstile, which a headless browser never passes, so an e2e submit could not reach the reroute.

- **`client-built-output-clean`**: on a client site, `gate.mjs run build` scans the built HTML in `dist/` after a successful build and fails on an HTML comment, a comment inside an inline script, (read by a JavaScript scanner: a trailing `//` comment counts, and `//` or `/*` inside a string, a template literal or a regular expression does not, including a regular expression right after a control statement's parenthesis, `if (ok) /[/*]/`), or a source-platform name (the engine's list of site builders, extended by the overlay's `profiles.client.source_platforms`), naming the file; clean output passes, and internal repositories are not scanned. It needs no extra gate step.

- **`client-preview-noindex`**: when gate tests a client site against its Workers Builds preview, `gate.mjs e2e` first fetches the preview's home page and a path only the Worker can answer (`/__std-noindex-probe`, a 404; static `_headers` rules do not cover Worker-rendered responses) and fails unless both say `noindex` (the `noindex` or `none` directive in the `content` of a `<meta name="robots">`, attributes read in any order, quoting and spacing, and never one inside an HTML comment, `<noscript>` or `<template>`, or in an `X-Robots-Tag` header, optionally per bot), so a preview never gets indexed; a slow suite is never failed for its time; internal repositories are not checked. Production is the other half: its deploy command refuses HTML containing `noindex`.

- **`error-tracker-rerun-safe`**: the error-tracker setup (dry run, create, route, write the DSN) is a no-op on rerun, and a rerun after a closed mapping PR never deletes that branch (it may hold later work): it opens a new PR from the next free retry branch (`chore/sentry-project-retry/<repo>/<n>`) off the current default (reruns once broke on a leftover branch).

## Org settings (`org/`)

- **`org-rulesets-render`**: the org ruleset set renders from the overlay: PR rule and required `gate` (the only required check unless the overlay adds some) on default branches and `main`, squash merges with resolved review threads and code-owner review on every repository's default branch and `main` (one branch: no staged or staging rulesets), the sync App's bypass on the branch rulesets and none on the push-hygiene ruleset (a pack landing never adds a secret or large file; the removed `push_app_bypass` is refused); a live ruleset's extra approval for unattributed changes is kept unless the overlay sets it; the removed `review_status`, `review_thread_resolution` and `codex_verdict_status` settings, and the staged flow's `staged` and `extra_checks.staged_main` / `extra_checks.staging`, are refused.
- **`org-squash-commit-from-pr`**: `org-apply` sets every repository's squash commit to the PR title and the PR description (GitHub's `PR_TITLE` / `PR_BODY`, sent as the pair GitHub accepts), so each commit on the default branch carries the PR's What, Why and linked issue; a repository already set gets no write.
- **`gate-required-either-strict`**: every pull-request ruleset keeps `gate` required whether `strict_status_checks` is on or off; strict changes only the strict flag, and only on the squash-merge ruleset. Incident: strict off dropped the direct repos' required-checks rule, so `org-apply` would have removed `gate` there.
- **`org-one-flow`**: no ruleset or org property knows the staged flow: `org-apply` deletes the retired `flow` property (after the rulesets that read it), and refuses the overlay's staged settings. The squash-merge ruleset takes over the legacy direct-repos ruleset in place, and with the overlay's extra-approval setting unset it keeps the strictest value any legacy (direct, staged-main, staging) ruleset had, so migrating never loosens it; the staged ones are deleted.
- **`org-apply-idempotent`**: `org-apply --dry-run` shows the diff against live settings, and a second apply changes nothing.

## Engine

- **`workflows-parse`**: every workflow the engine ships parses as YAML (an unquoted colon once disabled a workflow silently).

- **`engine-neutral`**: no organization name, internal host, account, App or vault identifier appears in the tree or anywhere in history.
- **`gate-timeout-overlay`**: the shipped `std-gate.yml` gate job times out at 30 minutes unless the overlay sets `gate.timeout_minutes`, an integer from 5 to 120 (anything else is refused before anything is written); the repository's offline check accepts the rendered value.

- **`release-controlled-dotenv`**: every release Wrangler command uses a private empty explicit env file; build-created .env files cannot reload production override names, match tags or account values onto staging or secondary uploads. Incident: stripped child variables were reloaded by Wrangler before name resolution.
- **`release-resolved-resource-guard`**: after building, before any remote command, every resolved staging target is checked against all production resources, including generated D1/KV/R2, queue producers and consumers, Workflows, service bindings and Durable Object script names. A safe source config cannot hide production bindings in adapter output.
- **`staging-required-secrets-upgrade`**: apply repairs the missing or incomplete staging secrets.required declaration in actual 0.7.1 brochure migration output, preserving existing configuration and comments; applying again changes nothing.

- **`release-generated-production-inventory`**: release builds and snapshots each resolved production config before staging; bindings introduced by adapters in both environments cannot escape isolation checks, including before remote D1 migrations. Safe isolated generated bindings still deploy, and production gets a fresh final build.
- **`release-durable-object-transfer-guard`**: primary and secondary staging targets reject inherited and generated Durable Object transfers from any production Worker, and malformed migration/transfer declarations, before any remote command; a transfer from an isolated staging Worker remains allowed.

## Rollback-safe releases (expand/contract)

- **`rollback-expand`**: new expand-only SQL, including a rewrite of a newly added column, passes the real `--check`; comments, mixed case, quoted identifiers and semicolons inside strings are parsed safely.
- **`rollback-drop-column`**: DROP COLUMN in a second SQL statement fails with expand/contract guidance.
- **`rollback-rename`**: table and column RENAME fail.
- **`rollback-contract`**: a header marker with issue/PR reference and repo-local affected-object list passes with a note; a missing link fails.
- **`rollback-do-removal`**: removing a bound DO class export fails.
- **`rollback-production-binding`**: removing a previous production binding fails.
- **`rollback-draft`**: destructive SQL warns without failing a draft, and gate's checks job carries PR base and draft context into `--check`.
- **`rollback-hazards`**: existing-data rewrites, type narrowing, unsafe constraints, unlisted contract objects, DO deletion/rename migrations and each production binding kind fail; new schema and staging-only binding changes pass.

- **`rollback-nested-update`**: a nested WHERE cannot hide a later assignment to an existing column from setup.sh --check.
- **`rollback-persistent-sql`**: view deletion, unique indexes, triggers with DELETE and unclassified SQL require exact affected-object contracts through setup.sh --check.
- **`rollback-generated-production`**: clean-checkout builds of both revisions expose generated D1 migration directories and removed production bindings to setup.sh --check.
- **`rollback-cross-worker-do`**: a caller switching classes cannot permit the host to remove a class or delete its namespace required by the previous release.

- **`rollback-renamed-history`**: historical column/table renames retain existing targets; repeated CREATE cannot mark columns fresh, while genuinely added columns pass setup.sh --check.
- **`rollback-schema-replace`**: plain inserts inheriting column or table ON CONFLICT REPLACE require a contract; explicit non-replacing INSERT policies pass setup.sh --check.
- **`rollback-seed-do-nothing`**: targeted and bare ON CONFLICT DO NOTHING seeds pass setup.sh --check, including inherited REPLACE schemas; DO UPDATE remains a hazard.
- **`rollback-build-bootstrap`**: with no pnpm on PATH, real dependency installation and both revision builds use the temporary Corepack environment through setup.sh --check, then clean it up.

- **`rollback-push-base`**: a shallow feature-only push checkout with origin recovers the default branch and rejects destructive SQL through setup.sh --check; missing comparison data with any remote fails even for drafts, while only repositories without remotes may skip with a note.
- **`one-test-job`**: the full gate is `checks` plus ONE `test` job (the jobs are `checks`, `test`, `gate`): one checkout, one install with the cache restores, then typecheck, build, `gate.local.sh`, the Workers Builds preview step and the affected e2e, in that order; `gate` needs exactly those two and keeps its name, passing only when both succeed on a ready pull request, and failing on a failed or skipped `test`. Renaming `build`, `e2e` and `repo` away is not breaking: only `gate` is a required check.
- **`one-gate-run-per-push`**: a draft pull request is not gated: `checks` and `test` are skipped for any event on a draft and the gate job is skipped too, named `draft (not gated)` (verified live: a skipped job's expression name is posted unevaluated, so no check is called `gate` on a draft head; the ready run posts `gate`). A ready run queued before `pr.sh review-round` converted the PR to draft is covered too: the plan's live draft output (`rollback_draft`) skips `test` and `gate` and names the gate job `draft (not gated)`, so there is no false red `gate`; marking it ready again runs the full gate (the verdict still fails a draft head or an untested ready head). The push-then-`ready_for_review` sequence therefore bills one run, not a cancelled one plus a full one, and nothing is red on a draft push; a run cancelled by a newer one in its group posts no `gate` (`!cancelled()`). Incident: three consumer pushes each started a cancelled-but-billed run 7-12 s before the full one (run pairs 37695603321/37695620976, 37696412563/37696447458, 37698673411/37698693704).
- **`draft-head-never-passes-gate`**: a draft head carries no `gate` (see `one-gate-run-per-push`), and the verdict is the second guard: it fails a draft head whatever the job results (the cheap plan, the live draft flag at plan time, or `checks` skipped), so a pull request flipped to ready by an Actions token, which fires no `ready_for_review` run, has no passing `gate` to merge on.
- **`gate-run-name`**: a `pull_request` run of `std-gate` is named `gate pr=<n> base=<ref> head=<40-hex sha>` (the launcher parses it when GitHub returns an empty `pull_requests[]`); the expression is empty for every other event, which keeps GitHub's default run name (verified live).
- **`affected-e2e-narrows-only-on-specs`**: a pull request runs only the e2e specs it changes when every changed file is an added or modified `*.spec.*` / `*.test.*` under an `e2e/` directory (a pull request into `main` included, and only when `GITHUB_EVENT_NAME` is exactly `pull_request`: missing, empty or another event runs the whole suite); any other change (source, a helper, a fixture, setup or `globalSetup`, configuration, docs, a unit test, a deletion or a rename) runs the whole e2e suite. Unit tests and repo checks always run in full.
- **`affected-opt-out`**: `"affected": false` in `standards.json`, `GATE_SELECT=full` and a base that cannot be found each run the whole e2e suite; `--check` refuses a non-boolean `affected`.
- **`affected-runners`**: gate's e2e step hands a spec-only change to `playwright test` (escaped file filters, the run's `--project`) and to `node --test`, runs the whole suite otherwise, and gives the project and file arguments only to a package script that is exactly a bare `playwright test` (`playwright test --grep @smoke` and `&&` chains run unchanged); a custom `e2e` command runs as written with `GATE_AFFECTED` and `GATE_AFFECTED_E2E` in its environment, and `GATE_SELECT=full` whenever the whole suite runs.
- **`affected-full-runs-every-project`**: with a real multi-project Playwright config, `GATE_SELECT=full` (the release check) builds the runner command with no `--project` and no positional `tests/e2e`, so a failing spec outside `tests/e2e` (an `api` project) fails the run; a pull request, the merge queue and a manual re-gate run the Chromium project only and never narrow. The e2e step carries no time limit (no suite timeout, kill signal or fetch deadline).
- **`gate-concurrency-groups`**: `std-gate`'s concurrency group is per pull request, with `-edit` for a description edit and `-draft` for a draft-payload run, so a draft `synchronize` (every job skipped) and the `ready_for_review` of the same pull request land in different groups and the draft run can never cancel the full gate (a push to a draft followed by ready creates both runs in either order); two ready `synchronize` runs share a group (a newer push cancels the older full gate); merge_group and workflow_dispatch keys are unchanged. Incident: PR #84's own ready run 37722695810 was cancelled by the draft run 37722696294.
